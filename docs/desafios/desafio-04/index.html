Visão Geral

Objetivo: fazer o deploy de uma aplicação Node.js no Minikube e acessá-la no browser via Ingress.

src/app.js
Servidor HTTP Node.js puro com 4 rotas: / /health /health/ready /metrics — graceful shutdown incluído.
Dockerfile
Multi-stage build — stage builder (npm install) + stage runtime (USER node, HEALTHCHECK).
k8s/ (10 manifests)
Namespace · ServiceAccount · ConfigMap · Secret · Deployment · Service · Ingress · HPA · PDB · NetworkPolicy.
ⓘ Todos os arquivos de código estão em src/desafios/desafio-04/ na raiz do repositório.
1

Subir o Minikube

Abra o Docker Desktop manualmente e aguarde estabilizar. Depois, em um PowerShell comum (sem admin):

minikube start --cpus=2 --memory=2048 --driver=docker
✓ Aguarde a mensagem "Done! kubectl is now configured" antes de continuar.
2

3

Build da Imagem dentro do Minikube

A imagem precisa ser buildada dentro do Minikube (não no Docker Desktop local) porque o Deployment usa imagePullPolicy: Never:

# A partir da raiz do projeto devopslab
minikube image build -t devops-app:v1.0 src/desafios/desafio-04

# Confirmar que a imagem existe no Minikube
minikube image ls | grep devops-app
⚠ imagePullPolicy: Never — se o build não for feito dentro do Minikube, os pods vão falhar com ErrImageNeverPull.
4

Aplicar os Manifests Kubernetes

# Aplicar todos os manifests em ordem
kubectl apply -f src/desafios/desafio-04/k8s/

# Aguardar os 3 pods ficarem prontos (timeout 120s)
kubectl rollout status deployment/app-deployment -n app --timeout=120s

# Verificar pods
kubectl get pods -n app

# Verificar services
kubectl get svc -n app
✓ Devem aparecer 3 pods com status Running no namespace app.

O que cada manifest cria

00-namespace
Namespace app — isolamento de todos os recursos.
01-serviceaccount
ServiceAccount + Role (get/list pods, configmaps, secrets) + RoleBinding.
02-configmap
NODE_ENV=production · LOG_LEVEL=info · PORT=3000 · METRICS_ENABLED=true
03-secret
Opaque Secret com DATABASE_URL, REDIS_URL, JWT_SECRET (valores de dev).
04-deployment
3 réplicas · RollingUpdate · liveness + readiness + startup probes · securityContext nonRoot · preStop sleep 5.
05-service
ClusterIP porta 80→3000 + NodePort porta 30080→3000.
06-ingress
Ingress nginx · host app.local · rotas / /api /health /metrics.
07-hpa
HPA · min 3 / max 10 réplicas · CPU 70% · Memory 80%.
08-pdb
PodDisruptionBudget · minAvailable 2.
09-networkpolicy
Ingress do namespace ingress-nginx e app · Egress DNS + HTTPS + interno.
5

Habilitar Ingress e Configurar Acesso

# Habilitar o addon de Ingress nginx no Minikube
minikube addons enable ingress

# Terminal Admin — manter aberto enquanto usar o Ingress
minikube tunnel

Adicionar ao arquivo C:\Windows\System32\drivers\etc\hosts (requer admin):

127.0.0.1  app.local
# Adicionar via PowerShell Admin
Add-Content -Path "C:\Windows\System32\drivers\etc\hosts" -Value "127.0.0.1  app.local"
⚠ O terminal do minikube tunnel precisa ficar aberto enquanto usar o Ingress. Fechar o terminal derruba o túnel.

Troubleshooting

Página nginx de boas-vindas

O que significa: O Ingress está ativo e respondendo, mas os pods da aplicação ainda não terminaram de subir. O nginx não sabe para onde rotear o tráfego e exibe sua própria página padrão.

O que fazer: Aguarde 30–60 segundos e recarregue o browser. Verifique se os 3 pods estão Running: 

kubectl get pods -n app
ERR_NAME_NOT_RESOLVED

O que significa: O browser não consegue resolver o nome app.local para um IP. O sistema operacional não sabe que esse domínio existe pois a entrada não foi adicionada ao arquivo hosts.

O que fazer: Verifique se a linha abaixo existe em C:\Windows\System32\drivers\etc\hosts (requer PowerShell Admin): 

127.0.0.1  app.local

# Para adicionar via PowerShell Admin:
Add-Content -Path "C:\Windows\System32\drivers\etc\hosts" -Value "127.0.0.1  app.local"
ErrImageNeverPull

O que significa: O Deployment tem imagePullPolicy: Never — o Kubernetes nunca tenta baixar a imagem de um registry externo, só usa imagens locais do Minikube. Se o build foi feito no Docker Desktop local em vez de dentro do Minikube, a imagem não existe no contexto correto e o pod não consegue subir.

O que fazer: Refaça o build dentro do Minikube a partir da raiz do projeto: 

minikube image build -t devops-app:v1.0 src/desafios/desafio-04

# Confirmar que a imagem existe no Minikube
minikube image ls | grep devops-app
Pods em CrashLoopBackOff

O que significa: O pod sobe, falha, reinicia e falha de novo — entra em loop. As causas mais comuns são: erro no código do app.js, variável de ambiente ausente, ConfigMap ou Secret com valor incorreto, ou problema de permissão com o usuário node (uid 1000).

O que fazer: Veja o log do pod para identificar a mensagem de erro exata: 

# Ver logs do pod (substitua pelo nome real)
kubectl logs <nome-do-pod> -n app

# Listar pods para copiar o nome
kubectl get pods -n app

# Ver eventos de erro no namespace
kubectl get events -n app --sort-by=.lastTimestamp
