Visão Geral

Objetivo: fazer o deploy de uma aplicação full-stack no Minikube com dois containers independentes no mesmo namespace, comunicação interna via Service, proxy reverso no Nginx, e acesso externo via Ingress.

Frontend — Nginx SPA
React + TypeScript + Vite compilado para dist/. Servido pelo Nginx na porta 80. Proxy /api → backend interno.
Backend — Node.js API
Express na porta 3001. Autenticação por PIN. Conexão dinâmica ao MongoDB Atlas. Web Push (VAPID). Cron jobs diários.
k8s/ (13 manifests)
Namespace · ServiceAccount · 2× ConfigMap · Secret · 2× Deployment · 3× Service · Ingress · HPA · PDB · NetworkPolicy · kustomization.
ⓘ Este desafio é a evolução do Desafio 4. A principal diferença está na arquitetura: dois runtimes distintos (Nginx + Node.js), imagem via registry externo (GHCR em vez de local), secrets obrigatórios em runtime e namespace isolado coexistindo com o namespace app do Desafio 4.

Autenticar no GHCR e Criar imagePullSecret

As imagens são privadas no GitHub Container Registry. O Kubernetes precisa de credenciais para fazer o pull.

3a. Gerar Personal Access Token (PAT)

Acesse github.com → Settings → Developer settings → Tokens (classic) → Generate new token (classic) e marque apenas o escopo read:packages. Copie o token gerado (ghp_xxx...).

⚠ O escopo read:packages é diferente das permissões de repositório. Ter acesso ao código não concede acesso às imagens Docker automaticamente.

3b. Login e imagePullSecret

# Login no GHCR com o PAT
echo "ghp_SEU_TOKEN" | docker login ghcr.io -u SEU_USUARIO_GITHUB --password-stdin

# Criar namespace (necessário antes do secret)
kubectl create namespace financial

# Criar imagePullSecret no cluster
kubectl create secret docker-registry ghcr-secret \
  --docker-server=ghcr.io \
  --docker-username=SEU_USUARIO_GITHUB \
  --docker-password=ghp_SEU_TOKEN \
  -n financial

# Confirmar pull das imagens
docker pull ghcr.io/vibecodia/vibecodia-finances-frontend:latest
docker pull ghcr.io/vibecodia/vibecodia-finances-backend:latest
✓ Ambos os Deployments referenciam imagePullSecrets: [{name: ghcr-secret}] — o secret criado aqui é usado automaticamente.

Configurar Secrets da Aplicação

O backend precisa de 3 secrets obrigatórios. Sem eles, o processo Node.js encerra na inicialização. Os valores nunca são commitados no repositório — são injetados via kubectl.

MONGO_CONN_MAP
JSON com mapa PIN → URI MongoDB Atlas. Cada usuário tem um PIN único e seu próprio banco. Exemplo: {"1234":"mongodb+srv://user:pass@cluster.mongodb.net/db"}
VAPID_PUBLIC_KEY
Chave pública para Web Push Notifications. Gerada uma única vez e reutilizada. Se perder, todos os dispositivos cadastrados param de receber notificações.
VAPID_PRIVATE_KEY
Par da chave pública. Nunca exposta ao browser. Usada para assinar os payloads de push notification.

Gerar VAPID keys (uma única vez)

# Gera as chaves dentro do container — formato garantido para web-push@3.x
docker run --rm ghcr.io/vibecodia/vibecodia-finances-backend:latest node -e "
const wp = require('./node_modules/web-push');
const k = wp.generateVAPIDKeys();
console.log('PUBLIC:' + k.publicKey);
console.log('PRIVATE:' + k.privateKey);
"
⚠ Não use npx web-push generate-vapid-keys — versões diferentes do Node.js geram formatos incompatíveis. Gere sempre dentro do container do backend.

Criar o secret no cluster

# Salvar o MONGO_CONN_MAP em arquivo (evita problemas de escaping no PowerShell)
# Substituir PIN, user, pass, cluster e db pelos valores reais
$Utf8NoBom = New-Object System.Text.UTF8Encoding $False
[System.IO.File]::WriteAllText(
  "$env:TEMP\mcm.txt",
  '{"SEU_PIN":"mongodb+srv://user:pass@cluster.mongodb.net/db?retryWrites=true&w=majority"}',
  $Utf8NoBom
)

# Criar secret (idempotente — pode rodar novamente para atualizar)
kubectl create secret generic financial-app-secret \
  -n financial \
  --from-file=MONGO_CONN_MAP="$env:TEMP\mcm.txt" \
  --from-literal=VAPID_PUBLIC_KEY="CHAVE_PUBLICA_GERADA" \
  --from-literal=VAPID_PRIVATE_KEY="CHAVE_PRIVADA_GERADA" \
  --dry-run=client -o yaml | kubectl apply -f -

# Confirmar conteúdo sem BOM (primeiro byte deve ser 123 = '{')
kubectl get secret financial-app-secret -n financial \
  -o jsonpath='{.data.MONGO_CONN_MAP}' | ForEach-Object {
    [System.Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($_))
  }

Aplicar os Manifests via Kustomize

kubectl apply -k src/desafios/desafio-11/k8s/ --dry-run=client
# Esperado: 19 recursos criados (dry run), 0 erros

# Aguardar frontend (2 réplicas)
kubectl rollout status deployment/financial-deployment -n financial --timeout=120s

# Aguardar backend (1 réplica)
kubectl rollout status deployment/backend -n financial --timeout=120s

# Verificar todos os pods
kubectl get pods -n financial
✓ Devem aparecer 3 pods Running: 2 × financial-deployment + 1 × backend.

O que cada manifest cria

00-namespace
Namespace financial — isolado do namespace app do Desafio 4.
01-serviceaccount
SA financial-app-sa + Role (get ConfigMap/Secret) + RoleBinding.
01b-deployer-sa
SA financial-deployer para CI/CD — Role mínima: patch/update Deployment + watch Pods.
02-configmap
nginx.conf com try_files para SPA routing e proxy_pass para http://backend:3001.
03-secret
Opaque Secret — MONGO_CONN_MAP + VAPID_PUBLIC_KEY + VAPID_PRIVATE_KEY. Apenas placeholders no repo.
backend-configmap
PORT=3001 · NODE_ENV=production · TZ=America/Sao_Paulo.
backend-deployment
1 réplica fixa — cron jobs duplicariam com múltiplas réplicas. RollingUpdate + probe em /api/health-check.
backend-service
ClusterIP name backend porta 3001 — o nome é crítico: o nginx.conf faz proxy_pass http://backend:3001.
04-deployment
Nginx SPA · 2 réplicas · RollingUpdate zero-downtime · probe em /health · nginx.conf montado via ConfigMap.
05-service
ClusterIP 80→80 + NodePort 30800 para acesso direto sem Ingress.
06-ingress
Host financial.local · path /api → backend · path / → frontend.
07-hpa
HPA frontend · min 2 / max 8 réplicas · CPU 60% · Memory 80%.
08-pdb
PodDisruptionBudget · minAvailable 1 — sempre 1 réplica disponível durante manutenção.
09-networkpolicy
Ingress: ingress-nginx + pods internos. Egress: DNS + MongoDB Atlas porta 27017 + tráfego interno.

Configurar Acesso via Ingress

# Terminal Admin — manter aberto enquanto usar o Ingress
minikube tunnel

Adicionar ao arquivo C:\Windows\System32\drivers\etc\hosts (requer admin):

127.0.0.1  financial.local
# Adicionar via PowerShell Admin
Add-Content -Path "C:\Windows\System32\drivers\etc\hosts" -Value "127.0.0.1  financial.local"

Ou acessar via port-forward sem necessidade de Ingress:

# Mantém o terminal aberto — acesse http://localhost:8080
kubectl port-forward -n financial svc/financial-service 8080:80
⚠ O minikube tunnel precisa ficar aberto enquanto usar o Ingress. O port-forward é a alternativa mais simples para testes locais.

Troubleshooting

ImagePullBackOff

Causa: o secret ghcr-secret não existe, está com token expirado, ou a conta não tem permissão read:packages no pacote da org.

kubectl get secret ghcr-secret -n financial
kubectl describe pod -n financial -l app=financial-app | Select-String "pull"
Backend CrashLoopBackOff

Causa mais comum: VAPID key com formato inválido ou MONGO_CONN_MAP com JSON malformado (BOM no início do arquivo).

kubectl logs -n financial -l app=backend --tail=20
# Se "Vapid public key should be 65 bytes": gere as keys dentro do container (Step 4)
# Se "Erro ao parsear MONGO_CONN_MAP": verifique BOM no arquivo com:
kubectl get secret financial-app-secret -n financial \
  -o jsonpath='{.data.MONGO_CONN_MAP}' | ForEach-Object {
    $b = [Convert]::FromBase64String($_)
    "Primeiro byte: $($b[0]) (deve ser 123 = '{')"
  }
Frontend CrashLoopBackOff — Permission denied

Causa: securityContext.runAsUser: 101 impede o Nginx de criar /var/cache/nginx. A imagem precisa iniciar como root para criar os diretórios temporários.

# Verificar o nginx.conf dentro da imagem — se tiver "user nginx;" precisa iniciar como root
docker run --rm --entrypoint cat ghcr.io/vibecodia/vibecodia-finances-frontend:latest /etc/nginx/nginx.conf | Select-String "^user"
# Se retornar "user  nginx;" → remover runAsNonRoot e runAsUser do securityContext
502 Bad Gateway via Ingress

Causa mais comum: NetworkPolicy bloqueando o Ingress Controller. O namespace ingress-nginx precisa ter o label app.kubernetes.io/name: ingress-nginx para a policy liberar.

# Verificar labels reais do namespace ingress-nginx
kubectl get namespace ingress-nginx --show-labels
# O label no namespaceSelector da NetworkPolicy deve bater exatamente

CI/CD — GitHub Actions

O workflow .github/workflows/ci-cd.yml automatiza build, push e deploy a cada push na branch main que altere arquivos em src/desafios/desafio-11/.

Push para main
  │
  ▼ Job: ci  (sempre — inclusive em PRs)
  ├── npm ci
  ├── npm run build  (Vite → dist/)
  └── upload artifact dist/
  │
  ▼ Job: docker  (somente main)
  ├── docker/login-action → ghcr.io
  ├── docker/build-push-action
  └── tags: sha-<7-chars-commit> + latest
  │
  ▼ Job: deploy  (somente main · environment: production)
  ├── kubectl set image deployment/financial-deployment ...
  ├── kubectl rollout status --timeout=120s
  └── kubectl get deployment/pods/svc -n financial

Secrets necessários no GitHub

KUBECONFIG
kubeconfig base64 do SA financial-deployer — Role mínima: patch Deployment + watch Pods. Nunca use kubeconfig de admin.
GITHUB_TOKEN
Automático — fornecido pelo GitHub Actions. Usado para push no GHCR.

Obter token do SA deployer (Kubernetes 1.24+)

# Gerar token com duração de 1 ano para o SA financial-deployer
kubectl create token financial-deployer -n financial --duration=8760h

# Ou criar Secret permanente do tipo service-account-token
kubectl apply -f - <<EOF
apiVersion: v1
kind: Secret
metadata:
  name: financial-deployer-token
  namespace: financial
  annotations:
    kubernetes.io/service-account.name: financial-deployer
type: kubernetes.io/service-account-token
EOF
kubectl get secret financial-deployer-token -n financial \
  -o jsonpath='{.data.token}' | ForEach-Object {
    [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($_))
  }
ⓘ Configure o token obtido acima como secret KUBECONFIG em github.com → Settings → Secrets → Actions.
